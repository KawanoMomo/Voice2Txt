# ADR-draft: Ctrl+V の後、貼り付け先が読み終える前に次の確定版でクリップボードを上書きしない — 一定の間合いを空ける

- **ステータス**: 提案(未採番)
- **カテゴリ**: architecture
- **日付**: 2026-10-07
- **対象プロジェクト**: Voice2Txt
- **関連**: 仕様 4.3・4.4、BLK-owner-20261007-1330-1、ADR-draft clipboard-busy-retry-and-delivery-failed

## コンテキスト

確定版はクリップボードに入れてから Ctrl+V を SendInput で送って届ける。貼り付け先がクリップボードを読むのは自分の入力を処理した時で、
Ctrl+V を送った時ではない。処理待ちの発話があると、前の発話の Ctrl+V の直後(次の文字起こしの時間だけ後)に次の確定版がクリップボードを上書きし、
貼り付け先の処理が遅いと前の発話が欠け、次の発話が 2 回貼られていた。検証モードの貼り付けは同期に読むので、この競合が見えなかった。

## 検討した選択肢

1. Ctrl+V を送ってから一定時間(既定 500 ms)は次の確定版でクリップボードを上書きしない — 単純で、偽物で試せる。遅すぎる貼り付け先は守れない
2. 遅延レンダリング(`SetClipboardData(NULL)` と `WM_RENDERFORMAT`)で、貼り付け先が実際に読んだ時を知る — 正確に見えるが、
   クリップボード履歴(Win+V)など変更を監視するアプリが先に読むので「貼り付け先が読んだ」とは区別できない。読まれないときの上限も別に要る
3. 次の発話を 1 本ずつ、前の Ctrl+V の後に固定の時間だけ必ず遅らせる — 処理待ちが無いときの待ち時間まで延びる

## 決定

1 を採る。`PttOptions.PasteSettleMs`(既定 500 ms。設定項目にはしない)。待つのは「前の Ctrl+V から 500 ms 経っていない間にクリップボードへ書く」ときだけで、
前の Ctrl+V の後に押した発話は押下(0.3 秒以上)と文字起こしでふつう経ち終えているので、処理待ちが無いときの待ち時間は変わらない。退避・入力失敗では Ctrl+V を送らないので数えない。

## 結果

- 検証モードの台本に `pasteReadDelay`(ms)を足し、遅い貼り付け先を指示できる(junior-4)
- 処理待ちの発話は、前の Ctrl+V から最大 500 ms 遅れて届く
- Ctrl+V を 500 ms 以上遅れて処理する貼り付け先では、処理待ちのある連投で競合が残る
