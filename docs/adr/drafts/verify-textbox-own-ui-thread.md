# ADR-draft: 検証モードの状態ごとのスクショが貼り付けを待たせる — 検証用のテキスト欄を自分の UI スレッドで動かす

- **ステータス**: 提案(未採番)
- **カテゴリ**: architecture
- **日付**: 2026-11-02
- **対象プロジェクト**: Voice2Txt
- **関連**: ADR-draft verify-screenshot-own-overlay-only、BLK-primary-20261008-1123-friction

## コンテキスト

検証モードはオーバーレイの状態が変わるたびに UI スレッドで `Refresh` → 40ms 待ち → `SaveScreenshot`(1 回約 60ms)を行う。
検証用のテキスト欄も同じ UI スレッドにあり、`TextBoxPaster.SendPaste` は `Invoke` でそこへ貼る。発話の間にショートカットを挟むと
取り消しのたびに状態が増え、貼り付けがスクショの後ろで待ち、`releaseToDeliverMs` が状態の数だけ延びた(中央 +25%)。
実機の貼り付け先は別のプロセスで、オーバーレイの描画を待たない。実機では撮影しないので利用者の待ちではないが、モデルごとの中央値の比較が歪む。

## 検討した選択肢

1. スクショを非同期にする(40ms 待ちを `await` にする) — 待っている間に次の状態が `Apply` されると、記録の状態と画が食い違う。BitBlt と照合の時間は残る
2. スクショに使った時間を数えて `releaseToDeliverMs` から引く — 製品側(Core)の計測に検証モードの補正が入り込み、実測でなくなる
3. 検証用のテキスト欄を専用の STA スレッドで動かす — 貼り付けはオーバーレイの UI スレッドを通らない。実機(別プロセスの貼り付け先)の形に近い

## 決定

3 を採る。`VerifyTextForm.StartOnOwnThread` がスレッドを立ててテキスト欄を表示し、ハンドルを返す(他スレッドから `Handle` を読まない)。
結果の `textbox` は最後にそのスレッドから読む。スクショの撮り方・状態の記録・製品の貼り付けの経路は変えない。

## 結果

- ショートカットの有無で「離してから貼り付け − 文字起こし」の中央値の差が 10ms 未満になる(数値は BLK に記録)
- オーバーレイとテキスト欄の描画が別スレッドになる。テキスト欄はスクショの範囲に入らないので画は変わらない
